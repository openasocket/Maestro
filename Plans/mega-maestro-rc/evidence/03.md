## Failed attempts, preserved

- The runtime's `processEpoch` was an ISO timestamp and fails the endpoint's
  identifier rule (`[A-Za-z0-9][A-Za-z0-9_-]{0,127}`); the attachment
  validator refused it locally before a byte was sent (test
  `does not send an attachment it cannot describe`). `installationIdentity()`
  now mints a hex epoch and the runtime uses it (MRC-03-04).
- First client suite run: 14 of 15. The failing assertion expected an
  oversized answer to an effectful request to read `unavailable`; the request
  had fully left the process, so `unknown` is the right answer. The test now
  asserts `unknown` there and `oversized` on a read-only request.
- First policy-status run: 2 of 3 failed because the fake daemon stamped
  the approval expiry from the real clock while the test ran on a fixed one,
  so the registration read as lapsed. The fake gained a `now` knob; no
  product code changed.
- First service-composition run: 2 of 3 failed and found a real defect: the
  adapter's authority id was fixed at construction, so a desktop composed
  before it enrolled would have stayed `unavailable` until restart. It now
  follows the record and leases read it at mint (`c675ba1`).
- `projectPolicyStatus` called an observation from the future `fresh`; it is
  now `unknown` (a clock the host cannot trust).
- `npm run docs:verify` after the canonical entries: 2 findings (index
  lines over 320 chars). Shortened; 0 findings.
- The first esbuild driver invocation ran the native `esbuild` binary under
  `node` and failed on the Mach-O header; the JavaScript API bundled it.

## Real endpoint attempt (not a pass)

The daemon is the sibling's own compiled endpoint (`apps/endpoint/dist` at
`d5143a6`, development mode), started on a scratch workspace inside this
checkout and stopped with its own `stop` verb. The client is this branch's
`createLocalEndpointClient()`, unmodified, bundled into a driver that calls
`compatibility`, `attach`, `registration.challenge`, `registration.redeem`
and `invoke('execution')` in that order and prints what came back:

```json
{
	"platform": "darwin",
	"compatibility": { "status": "denied", "reason": "unauthenticated" },
	"attach": { "status": "denied", "reason": "unauthenticated" },
	"challenge": { "status": "denied", "reason": "unavailable" },
	"redeem": {
		"status": "unavailable",
		"reason": "no-challenge",
		"message": "No challenge is open on this connection."
	},
	"executionWithoutSession": {
		"status": "unavailable",
		"reason": "not-attached",
		"message": "This connection is not attached; attach() first."
	},
	"state": {
		"connection": 1,
		"attached": false,
		"status": null,
		"registration": "none",
		"closed": false
	}
}
```

What this proves: the real daemon accepted the real client's framing (HTTP
over its private Unix socket, protocol-1 envelope, bounded body) and
answered inside the envelope with its own refusals; the client read those
answers against its correlation ids, called none of them authority, refused
to redeem with no open challenge, and refused to send an operation on an
unattached connection. What it does not prove: registration, policy status
or revoke. On macOS the daemon's native peer authentication is unsupported
(`IPC_PLATFORM_UNSUPPORTED` in `apps/endpoint/src/ipc/native.ts`), so every
peer is `unauthenticated` and a challenge is `unavailable` before any
enrollment question arises; and the daemon is unenrolled, with no
Mega-Maestro API behind it to enroll against or approve a registration in.

The owned Linux harness the task names was not available: Docker is
installed (server `linux 29.9.1`), but the sibling's packaged application
artifacts (`artifacts/application/0.1.0/*`, newest `2f7206b0` built
2026-10-11) are all `sourceDirty: true`, built on `darwin/arm64`, and the
native peer module (`apps/endpoint/native/peer.node`) is not built; building
it, the API, its database and the console in a container to approve a
