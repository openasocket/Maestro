## Approved local gateway route (real Maestro code, declared double)

The exercise runs the built library at HEAD: `bindApprovedCredentials()`,
`buildAgentLaunchPlan()` with a route ceiling, `createContextVerifier()`,
`createLocalHostAuthority()` with a policy table, `buildDispatchSnapshot()`,
and `startTurn()` with the lease re-checked at the spawn. Two loopback HTTP
listeners stand in for the approved gateway and for an "external" origin.
The provider is an inline Node program labeled `claude-code` for the route
that does what a provider does with its environment: reads
`ANTHROPIC_BASE_URL` and `ANTHROPIC_API_KEY` and sends one request. No real
provider, account or paid model is involved, and the report says so. The
approved value is a random canary in a systemd-style credentials directory;
the user's override sets a personal key, the external base URL and a forged
`MAESTRO_MANAGED_LEASE` on the agent's own env vars.

`secretValueInReport: false`: the canary is in no line of the report. The
user override therefore caused zero external effect under management, by
environment (stripped and pinned) and by argument (refused before any
spawn), while the same input unmanaged reached the external origin.

## Capability limitations and named dependencies

- The credential, routing and account seams are implemented and exercised
  with injected policy tables, a labeled provider double and loopback
  listeners. No real provider route is qualified by them: a real Claude,
  Codex or OpenCode launch under management has not been run against a real
  gateway, because none is configured and no paid traffic is authorized.
- The runtime's own managed turn composition (`runtime/turns.ts`) and the
  synthetic harness route still pass no `launch` input: the endpoint's
  execution binding (`route.credentialRef`, `route.destination`) is what
  will supply the ceiling, and that producer is CP-01's. The dispatch
  bridge and `runAgentTurn` carry it today.
- Translation governance decides nothing itself; the host's verified peer
  answers each step. With CP-02 (the Maestro runtime adapter) and CP-03
  (delegated workflow authority) still unavailable, the governance in this
  build has been driven only by injected tables.
- The pair check remains `ready: false` with the same dependencies as phase
  04: CP-01 (no contracts pin, no clean Linux endpoint artifact), CP-02
  (adapter `unsupported`), registration approval (no API). Owner:
  mega-maestro.
