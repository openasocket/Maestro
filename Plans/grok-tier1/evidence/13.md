## GT1-13-05 IMPLEMENT: `--sandbox` for read-only containment

**Outcome: profile identified offline, deliberately not wired, at `7766a8e437dc77094f3f0c4b1df25c3f94c7123f`. `readOnlyArgs` is unchanged and the readiness gate `external:grok-readonly-cli-enforcement-unqualified` stays open.**

Offline sources (0 paid calls, isolated empty `GROK_HOME` under `/tmp`, temporary cwd):

- `grok --help`: `--sandbox <PROFILE>  Sandbox profile for filesystem and network access [env: GROK_SANDBOX=]`. `grok inspect --json` has no sandbox field, with or without the flag.
- The 1.0.70 binary writes its user guide into `GROK_HOME/docs/user-guide/` on first run. `18-sandbox.md` (sha256 `82f3ca41b20a4b393cfff26a138d02464590dbff833f1817cc569520a4154181`) and `26-config-reference.md` (`sandbox.profile`: `off / workspace / read-only / strict / string`) name the built-in profiles `off` (default), `workspace`, `devbox`, `read-only`, `strict`, plus custom profiles in `sandbox.toml`.
- `read-only`: read everywhere, write only `~/.grok/` and temp dirs, child network blocked on Linux (seccomp) and a no-op on macOS. `strict` also writes the cwd, so it is not read-only.
- `GROK_HOME=<tmp> grok --sandbox read-only inspect --json` exits 0 and appends `{"event_type":"ProfileApplied","profile":"read-only","platform":"macos/seatbelt","enforced":true,"restrict_network":true,"read_write_paths":[GROK_HOME and temp dirs]}` to `sessions/sandbox-events.jsonl`. `--sandbox bogus-profile` exits 1 with "Refusing to start with its protections missing".

Why it is not appended to `readOnlyArgs` (named conflict with the task's "append it" branch):

1. **The profile is fixed for the life of a session.** From the guide and the binary's own error string ("cannot resume this session under sandbox profile '...': it was created with '...'"): a resume that leaves out `--sandbox` gets the saved profile, and a resume that names a different one is refused. All 3 local sessions under `~/.grok/sessions` record `sandbox_profile: "off"` (`Working/gt1-13-05/sessions.mjs`, counts only). Maestro sets permission mode per turn and resumes with `--resume <id>`. So a read-only turn on a tab that ran full or standard would be refused. Going the other way, a full turn on a session that a read-only turn started would stay write-confined with nothing telling the person why. Read-only consults, group chat summaries, AI command and the composer's read-only toggle all go through `readOnlyArgs`.
2. **Built-in profiles fail open.** If a built-in profile cannot be applied, grok logs a warning and runs without enforcement. Only custom profiles refuse to start.
3. **Network is not denied on macOS.** The task asks for a profile that denies writes and network. On darwin that holds for writes only.

Changes: `capabilities.ts` gains `GROK_CAPABILITY_EVIDENCE.flagDecisions['--sandbox']` (basis, the three reasons, and the probe that would settle it), and the `supportsReadOnlyMode` retained note points to it. A comment in `definitions.ts` beside `readOnlyArgs` says why the flag is absent. `env.ts` is unchanged: `carriesReadOnlyArgs` and `permissionVocabularyOf` read `readOnlyArgs` from the definition, so a later wiring is enforced by the managed ceiling without a vocabulary edit. `--sandbox off` is not added to `FULL_ACCESS_MODE_VALUES`, because `off` is Grok's default rather than a full-access request (full access is `--always-approve`).

Settling probe, for whoever wires this: (a) one live `grok --resume <id-of-an-off-session> --sandbox read-only -p ...` turn, confirming the refusal and its exit code on the real binary; (b) a Maestro-side per-provider-session record of the profile a Grok session started with, so the planner can open a new session (or refuse by name) instead of resuming across profiles. Ephemeral read-only spawns that are never resumed (tab naming, AI command) could take `--sandbox read-only` safely once (b) exists. Containment stays unqualified until the GT1-11 policy cases run on the real binary.
