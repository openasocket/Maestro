## GT1-13-03 IMPLEMENT: Grok context window from the account models cache

**Outcome: implemented at `669766008bf386214c010a1efb0df960812d597a`, with the caller wiring split into the GT1-13-03A continuation. The gauge is still unknown for every Grok tab until 03A lands; deterministic pins are GT1-13-04's.**

- Observed offline (no turn, no credentials read): `~/.grok/models_cache.json` on 1.0.70 has top-level `fetched_at, grok_version, auth_method, origin, identity, etag, models`; each model entry is `{ info, api_key, env_key, api_base_url }`. The four visible models (grok-4.7, grok-4.7-build-fast, grok-4.6, grok-4.5) report `info.context_window` 256000 and `context_windows` [256000, 500000]; efforts are xhigh/high/medium/low (grok-4.5: high/medium/low). The audit text named `identity`, `auth_method` and `origin`; the per-model `api_key`, `env_key` and `api_base_url` are a further reason to copy nothing but ids, windows and effort values.
- No default model is recorded offline: `config.toml` has no model key and `settings_cache.json` is a signed payload. So a Grok tab with no configured model gets a window only when an owned ACP observation reported the account's current model (kept as `defaultModel`); otherwise it stays unknown rather than guessing from cache order.
- `src/main/agents/detector.ts`: `readGrokModelsCache(accountDir)`; `discoverGrokOptions` reads it from the account dir `resolveAgentAccountDir` already selected, records that account's windows through `recordGrokContextWindows` (patches the grok snapshot only when detection marked it ok; an unreadable cache drops the account's entry), and serves the model and effort menus from the cache only when the owned observation is absent, invalid, or carries no menu. The observation wins whenever it answers.
- `src/shared/agentCapabilities.ts`: `accountModelContextWindows` (account key to `{ windows, defaultModel? }`). One more file than the task named; the window has to live on the snapshot the renderer already reads.
- `src/shared/agentConstants.ts`: `getContextWindowForAgent(agentId, snapshot, selection?)`; grok returns the cached window only for a matching account key and model, own entries only, else `0`.
- `src/renderer/services/contextGroomer.ts`: stale `grok-composer-2.5-fast` replaced by the four 1.0.70 ids; the list is static renderer data and cannot read discovery.
- **Conflict named:** the Grok discovery suite asserted that no file is ever read (the earlier "native cache bytes ignored" rule, with `malformed`, `empty`, `hidden` and `stale` cache cases). This task overrides that rule by design. The afterEach now allows only `models_cache.json`; the four cases still pass because the owned observation answers and wins. A cache from an older binary (`grok_version` differs) is not rejected, because the binary version is not known without a probe, which discovery refuses; the binary rewrites the file itself.
- **Why a continuation:** the gauge callers (`src/renderer/utils/contextUsage.ts`, `src/renderer/hooks/agent/internal/contextTimelinePoint.ts`, `src/shared/maestro-lib/parsers/usage-aggregator.ts`) pass no model or account key today, so they need the agent's model and `resolveAgentAccountKey` threaded in; that is three more files, past this packet's bound. ## GT1-13-03A IMPLEMENT: Grok model and account threaded into the window lookup

Commit `33dcaf23a6cabaeb6e6ca0944ebd8d7b060aa247`. Files: `src/renderer/utils/contextUsage.ts`, `src/renderer/hooks/agent/internal/contextTimelinePoint.ts`, `src/shared/maestro-lib/parsers/usage-aggregator.ts`.

- **Selection:** `resolveGrokContextSelection(session, tab?)` returns `{ model, accountKey }`. Model is the tab's override, then the agent's, then the provider-level configured model; with none, `getContextWindowForAgent` keeps using the observed default from GT1-13-03. The account key is `resolveAgentAccountKey('grok', effectiveAgentCustomEnvVars(session.customEnvVars, providerEnv), homeDir)`, the attribution `useProviderProfiles` already uses.
- **Hot path stays synchronous:** the provider-level env and model are fetched once (`getCustomEnvVars('grok')`, `getConfig('grok')`) into a module cache and re-read after 30 s. Until that cache and `$HOME` resolve, the selection is `undefined` and the window `0`: a guessed default account could name another account's window. Remote agents get none, because discovery records windows for local accounts only.
- **Callers:** the timeline point's static-table rank passes the selection for the session and the event's tab; the live usage listener hands that resolved window to `estimateContextUsage`, so the gauge, the compaction warning and the timeline share one denominator. The renderer and shared `estimateContextUsage` take an optional selection. `recordTurn` and the CLI `send` hold no resolved account key and pass none; `getAgentContextWindow` in `process-listeners-wiring` and the group chat router keep `0` with their existing comments.
- **Not covered:** the synopsis and batch `estimateContextUsage` calls in `useAgentExecution.ts` (outside this packet's files) pass no selection, so a Grok synopsis entry has no context percentage. Global env vars are not consulted, matching `useProviderProfiles`.
