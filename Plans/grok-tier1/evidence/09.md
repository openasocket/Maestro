### Grok claims that currently lack pre-effect enforcement or a real producer

None of these is edited to passing here. Phase 09 rows in `parity.json` stay as they are
until GT1-09-13.

1. `providerRouteSupport('grok')` `child-process` managed `implemented`: launch admission
   only; tools, files, network, MCP and descendants of a running Grok are not governed
   (blockers `GT1-09-R01`, `GT1-09-R02`).
2. `supportsReadOnlyMode: true` and `readOnlyCliEnforced: true`: provider self-enforcement
   via plan mode and a deny rule; no Maestro sandbox, no network control, no exact-binary
   proof (`GT1-09-R03`).
3. Managed standard-mode Grok over ACP: every permission request is denied because no
   per-effect endpoint operation exists; there is no proof that ACP asks before every
   effect class (hooks, subagents, MCP meta-tools, provider network), and the effect is
   untyped (`GT1-09-R01`, `GT1-09-R04`).
4. ACP route identity: the route table has no ACP member, so inventory, install policy,
   probes and the cross-agent router cannot tell a managed Grok ACP turn from a headless
   one, and the spawn snapshot names the headless argv while the ACP spawner runs
   `agent stdio` (`GT1-09-R05`).
5. ACP version binding: the desktop snapshot starts with `agentVersion: null` and the
   negotiation accepts the version the peer reports; no qualified version range exists
   (`GT1-09-R06`).
6. Model and account attribution: the desktop spawn snapshot reads the model from
   `--model` only, but Grok emits `-m <model>`, so every Grok desktop snapshot carries
   `model: null`; the snapshot carries no account (`GT1-09-R07`).
7. SSH qualification depends on a remote endpoint attestation producer that is not
   paired here (`GT1-09-R08`).
8. MCP and subagent control: uninjected and synthetic only (`GT1-09-R09`, `GT1-09-R10`).
9. No-tools: no verified all-off switch; a required no-tools turn must refuse
   (`GT1-09-R11`, safety refusal already in the groomer since GT1-08-14).
10. DLP, privacy and provider network: Maestro's fetch gating governs Maestro's own
    requests only; no pre-effect DLP producer exists (`GT1-09-R12`).
11. Real endpoint admission: no enrolled endpoint, no real broker decision for a Grok
    launch (`GT1-09-R13`).

## GT1-09-02 route and permission ceiling

Source at the GT1-09-02 commit (implementation only; tests are GT1-09-03's).

- `src/shared/maestro-lib/providers/capabilities.ts`: `ManagedRoute` and `MANAGED_ROUTES` name `grok-acp`. For `grok` the row is standalone `implemented` (Grok ACP stdio turn through the shared ACP driver) and managed `unsupported`; its note names the gap: no qualified version range bound before launch and no real endpoint authority deciding permission requests (CP-01, CP-03). Every other provider reads standalone `unsupported`. The child-process row is unchanged, so managed read-only and full-access Grok turns keep the existing launch admission.
- `src/main/process-manager/types.ts`: `runsOnGrokAcpRoute(config)` is the rule for which spawns take ACP (a forwarded native command, or a Grok turn whose plan asked for `standard`), read off `config.permission`, which the spawn handler stamps from the launch plan after custom arguments are joined. `managedGrokAcpRefusal(config)` returns the existing structured refusal (`unavailable`, `capability-unsupported`) for an admitted ACP spawn while the row is not `implemented`, and states that no headless fallback is taken. Standalone launches and other routes return null.
- The permission ceiling side needed no change in these files: `managedArgsProblems` already reads `-m` and Grok's `--always-approve` (`yoloModeArgs`) and `--permission-mode bypassPermissions` against a pinned ceiling, and `managedPermissionModeRefusal` already denies a wider mode.
- Not wired: `GrokAcpSpawner.spawn` does not call `managedGrokAcpRefusal` and `wantsGrokAcp` still has its own copy of the rule. That file is outside GT1-09-02's two files, so continuation GT1-09-02B wires it before GT1-09-03.

## GT1-09-02B ACP spawner wiring

Source at the GT1-09-02B commit (`src/main/process-manager/spawners/GrokAcpSpawner.ts` only; tests are GT1-09-03's).

- `GrokAcpSpawner.spawn` calls `managedGrokAcpRefusal(config)` as its first statement, before the native-command checks, the prompt read, the native-session scope, the environment, the consent session and any process. A refusal goes through the spawner's existing `refuse` path (one `agent-error` on the tab, a warning log) and the result carries `managed: { state: 'unavailable', code: 'capability-unsupported' }`, the shape `ProcessManager.spawn` returns for an admission refusal. The spawn is not handed to the headless spawner or any other spawner.
- `refuse` gained an optional `managed` argument and appends "Nothing was started." only when the message does not already end with it, so existing refusal texts are unchanged and the managed message is not doubled.
- `wantsGrokAcp(config)` now returns `runsOnGrokAcpRoute(config)`, so the route decision and the managed refusal read one rule.
- Standalone behavior: with no `config.admission` the refusal is null and every later step is the code that was there before.
- What this does not prove: the refusal is a safety pass for an unqualified route. It is not managed ACP functionality; GT1-09-R01 and R06 (endpoint authority over permission requests, a version range bound before launch) still stand.
- Checks: tsc main 0, cli 0; eslint 0 on the file; the same 39 suites as GT1-09-02 (route table, inventory, process-manager types, ACP spawner): 1979 passed, 6 failed, the same 6 that fail at HEAD (cross-agent-router.managed x4, ProcessManager.serveSpawn GT1-02-10E0T x2). A deleted throwaway spec (3 cases) proved an admitted ACP spawn returns the managed refusal with no consent session opened, no process registered and one agent-error, a standalone spawn carries no `managed` field, and `wantsGrokAcp` follows the shared rule; with the change stashed its refusal case failed.
