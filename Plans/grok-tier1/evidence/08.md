### Repaired (Grok only)

File: `src/renderer/hooks/batch/useDocumentProcessor.ts`.

- **Failed or cancelled turn kept its ticks.** Before: a Grok turn that ticked a box
  and then ended on a rate limit, auth refusal, stop or watchdog kill left the box
  checked, `tasksCompletedThisRun` counted it, and the next pass skipped the task.
  Now, when `session.toolType === 'grok' && !result.success`, the new exported pure
  helper `restoreTasksCheckedByFailedTurn(contentAtDispatch, contentAfter)` unticks
  only the boxes that were unchecked at dispatch and are checked now (exact body or
  body-prefix match, since agents append a note; duplicate bodies by count; fenced
  code skipped through `forEachMarkdownLine`; CRLF preserved). The document is
  written back through `window.maestro.autorun.writeDoc(..., sshRemoteId)` and
  re-counted. Everything else the turn or the operator wrote stays. Annotated
  already-checked lines are left alone; a tick that cannot be matched (agent rewrote
  the line) is left and logged as `unmatched`.
- **Failed turn counts zero completions.** `tasksCompletedThisRun` is `0` for a
  failed Grok turn even if an unmatched tick remains, so stats and history never
  record a partial preamble as finished work. `newCheckedCount` stays the true disk
  count, so stall detection is unaffected.
- **Failure synopsis is the failure.** For a failed Grok turn `fullSynopsis` is
  `result.error` (or `[doc] Task failed`), never the streamed partial response.

Other providers keep the previous behavior exactly (every new branch is gated on
`isFailedGrokTurn`).

### Repaired

File: `src/renderer/hooks/batch/internal/useGoalRunner.ts`.

- **A failed Grok iteration's preamble drove the goal.** Before: markers were parsed
  from `result.response` whatever the outcome, so a Grok turn that streamed
  `<!-- maestro:goal-complete -->` (or a progress or deadlock marker) and then ended
  on an auth refusal, stop or watchdog kill could end the run as `completed`,
  `deadlock`, or move the progress bar. Now, when
  `session.toolType === 'grok' && !result.success`, the iteration is read as
  reporting nothing: progress carries the previous raw value, `complete` and
  `deadlock` are false. The iteration still counts, so the evaluator's stall and
  iteration limits end a run of repeated failures exactly as before (termination
  rules not relaxed). Its history body is `result.error` (or `Iteration N failed`),
  never the partial response. Other providers are unchanged (gated on the flag).
- **Handoff model fallback differed from the iteration's.** The handoff passed
  `config.model ?? session.customModel`, while the iteration's spawn used
  `config.model || ...`; an empty run value made the resumed handoff run on the
  agent default instead of the session model the iteration ran on. Both now use the
  same truthiness test (model and effort). Identical for any non-empty value.

Usage reported by a failed (non-limit) iteration is still added to the run totals:
it is spend the provider reported, and unknown usage stays unknown (nothing is
added when the turn reports none).

### Repaired (Grok only)

File: `src/cli/services/agent-spawner.ts` (+70/-10).

- **A Grok run with no native terminal record could read as a finished task.**
  Before: a clean exit with an empty stdout (the live parser saw no native frame, so
  its exit check returns null for ACP callers) resolved `completed` with no response,
  and a non-zero exit after a streamed partial answer with no `end` record resolved
  `completed-with-warning` (the generic "answer outranks a bare exit" rule). Now a
  Grok clean exit without a successful terminal record (`!capture.resultMessageSeen`,
  not interrupted, no in-band error) carries the explicit error `Grok exited without
a native terminal record. Any response is incomplete.`, and the answer-outranks
  rule applies to Grok only once a successful `end_turn` record was seen. A
  successful `end` followed by exit 1 (the `--max-turns` / wizard-recovery case
  pinned by the existing suite) still soft-succeeds.
- **Auth/rate-limit failures lost their category.** Before: the generic path ran
  `TurnCapture` with `classifyInBandErrors: false`, so a Grok
  `{"type":"error","message":...}` became raw text only, and `AgentResult` had no way
  to tell the Auto Run engine (which pauses and applies limit rules on
  `result.agentError`) that it was a rate limit or an expired credential. Now Grok
  classifies in-band errors with its own pattern bank, and the new
  `grokCliFailure()` puts the classified error (in-band first, else the non-zero
  exit's stderr) on the new optional `AgentResult.agentError` and leads `error`
  with its message, the provider's words kept in parentheses. `unknown` and
  `agent_crashed` classifications keep the error they had and set no
  `agentError`. Success, interruption and managed refusals pass through untouched.
  Other providers are unchanged (every new branch is gated on `toolType === 'grok'`).
