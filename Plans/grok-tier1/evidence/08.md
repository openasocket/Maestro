### Repaired (Grok only)

File: `src/renderer/hooks/batch/useDocumentProcessor.ts`.

- **Failed or cancelled turn kept its ticks.** Before: a Grok turn that ticked a box
  and then ended on a rate limit, auth refusal, stop or watchdog kill left the box
  checked, `tasksCompletedThisRun` counted it, and the next pass skipped the task.
  Now, when `session.toolType === 'grok' && !result.success`, the new exported pure
  helper `restoreTasksCheckedByFailedTurn(contentAtDispatch, contentAfter)` unticks
  only the boxes that were unchecked at dispatch and are checked now (exact body or
  body-prefix match, since agents append a note; duplicate bodies by count; fenced
  code skipped through `forEachMarkdownLine`; CRLF preserved). The document is
  written back through `window.maestro.autorun.writeDoc(..., sshRemoteId)` and
  re-counted. Everything else the turn or the operator wrote stays. Annotated
  already-checked lines are left alone; a tick that cannot be matched (agent rewrote
  the line) is left and logged as `unmatched`.
- **Failed turn counts zero completions.** `tasksCompletedThisRun` is `0` for a
  failed Grok turn even if an unmatched tick remains, so stats and history never
  record a partial preamble as finished work. `newCheckedCount` stays the true disk
  count, so stall detection is unaffected.
- **Failure synopsis is the failure.** For a failed Grok turn `fullSynopsis` is
  `result.error` (or `[doc] Task failed`), never the streamed partial response.

Other providers keep the previous behavior exactly (every new branch is gated on
`isFailedGrokTurn`).

### Repaired

File: `src/renderer/hooks/batch/internal/useGoalRunner.ts`.

- **A failed Grok iteration's preamble drove the goal.** Before: markers were parsed
  from `result.response` whatever the outcome, so a Grok turn that streamed
  `<!-- maestro:goal-complete -->` (or a progress or deadlock marker) and then ended
  on an auth refusal, stop or watchdog kill could end the run as `completed`,
  `deadlock`, or move the progress bar. Now, when
  `session.toolType === 'grok' && !result.success`, the iteration is read as
  reporting nothing: progress carries the previous raw value, `complete` and
  `deadlock` are false. The iteration still counts, so the evaluator's stall and
  iteration limits end a run of repeated failures exactly as before (termination
  rules not relaxed). Its history body is `result.error` (or `Iteration N failed`),
  never the partial response. Other providers are unchanged (gated on the flag).
- **Handoff model fallback differed from the iteration's.** The handoff passed
  `config.model ?? session.customModel`, while the iteration's spawn used
  `config.model || ...`; an empty run value made the resumed handoff run on the
  agent default instead of the session model the iteration ran on. Both now use the
  same truthiness test (model and effort). Identical for any non-empty value.

Usage reported by a failed (non-limit) iteration is still added to the run totals:
it is spend the provider reported, and unknown usage stays unknown (nothing is
added when the turn reports none).

### Repaired (Grok only)

File: `src/cli/services/agent-spawner.ts` (+70/-10).

- **A Grok run with no native terminal record could read as a finished task.**
  Before: a clean exit with an empty stdout (the live parser saw no native frame, so
  its exit check returns null for ACP callers) resolved `completed` with no response,
  and a non-zero exit after a streamed partial answer with no `end` record resolved
  `completed-with-warning` (the generic "answer outranks a bare exit" rule). Now a
  Grok clean exit without a successful terminal record (`!capture.resultMessageSeen`,
  not interrupted, no in-band error) carries the explicit error `Grok exited without
a native terminal record. Any response is incomplete.`, and the answer-outranks
  rule applies to Grok only once a successful `end_turn` record was seen. A
  successful `end` followed by exit 1 (the `--max-turns` / wizard-recovery case
  pinned by the existing suite) still soft-succeeds.
- **Auth/rate-limit failures lost their category.** Before: the generic path ran
  `TurnCapture` with `classifyInBandErrors: false`, so a Grok
  `{"type":"error","message":...}` became raw text only, and `AgentResult` had no way
  to tell the Auto Run engine (which pauses and applies limit rules on
  `result.agentError`) that it was a rate limit or an expired credential. Now Grok
  classifies in-band errors with its own pattern bank, and the new
  `grokCliFailure()` puts the classified error (in-band first, else the non-zero
  exit's stderr) on the new optional `AgentResult.agentError` and leads `error`
  with its message, the provider's words kept in parentheses. `unknown` and
  `agent_crashed` classifications keep the error they had and set no
  `agentError`. Success, interruption and managed refusals pass through untouched.
  Other providers are unchanged (every new branch is gated on `toolType === 'grok'`).

   callers share it), the shared resolver yields `completed`, and a success chain fired off
   a turn that never answered. Cue now fails that run with the CLI's wording, "Grok exited
   without a native terminal record. Any response is incomplete." (GT1-08-05), appended to
   stderr where a failed run's reason is read.

- **Lineage.** `bindCueManagedRun()` binds the shell run on the same lineage as a prompt run: the
  subscription, then the owning Grok agent (`delegation.chain`), the pipeline, the chain root and
  the event. The versioned text is the command itself.
- **Query source.** The child env carries `MAESTRO_QUERY_SOURCE=cue`, so a `maestro-cli send` the
  command launches is recorded as Cue's. The env is the engine's own (the server-mode allowlist
  when active). The owning agent's `GROK_HOME` or other custom env vars are not injected, the same
  as for every provider.
- **Command, resource and target admission.** Under management the route is judged first on the
  final plan (`local-shell` or `ssh-shell`). Both read `managed: 'unsupported'` in
  `cueShellRouteSupport()`, so a managed host refuses `unavailable` / `capability-unsupported`
  with nothing started. That is the explicit refusal of unsupported host authority. A qualified
  route (test double only) is admitted on the snapshot of exactly this spawn, attributed as
  `cue-shell` with `dir:<projectRoot>` and the SSH target. The gate is re-checked at `spawn()`, the
  pid is bound, and a revocation stops the child.
- **Ownership.** An unowned workflow is refused by the router (`runtime-unavailable`) before the
  executor is called.
- **Stop.** The router returns `stopped` before dispatch. The executor checks again after the SSH
  wrap and the PATH probe, and after admission, where it releases an unused lease.
- **Durable result.** Exit 0 is `completed`, any other exit is `failed` with its code and stderr,
  a timeout is `timeout`, and a revocation is `stopped` with `[managed-revoked]`. No path turns a
  failed, denied or stopped run into success. The router returns the result unchanged for the
  engine to persist to `cue_events`.
- **Encore.** The `maestroCue` gate sits in front of the engine (`src/main/ipc/handlers/cue.ts`),
  not in the executor.

## GT1-08-10 IMPLEMENT: Grok text and spawning in group chat

Date: 2026-11-01. Kind: IMPLEMENT. Local commit only (no push per CONTRACT).

### What was wrong

- `src/main/group-chat/output-parser.ts` (`extractTextFromAgentOutput`) read a Grok stream
  through the generic loop. Grok sends its answer as token-sized `text` deltas with the
  whitespace inside the payload. Grok also sends `thought` deltas, which the parser marks
  `isReasoning`. Grok's `end` record carries no answer text. So the loop did three wrong things:
  - It joined every delta with a newline. That split words, and it split moderator `@mention`
    tags across lines. This is the gap parity.json records at `output-parser.ts:120`.
  - It kept the thought deltas. That would hand the model's reasoning to the router as
    instructions, for example "I should ask @Bob ...".
  - It used the shared registry parser instance (`getOutputParser`). The Grok parser latches
    the turn's terminal outcome (`terminal`, `toolNamesById`). So once one read saw a failure,
    every later Grok read inherited it.
- Where this applies: the moderator, participant, synthesis, recovery and resumed follow-up
  turns, plus the consult runner. They all read text through this one function
  (`exit-listener.ts` `reportGroupChatTurn` and `consult-runner.ts`).

### What changed

`output-parser.ts` gains `extractGrokText`, used when `agentType === 'grok'`:

- It parses with a fresh `createOutputParser('grok')`. This is the shared Grok parser, so there
  is no second parser.
- It concatenates the non-reasoning `text` deltas directly. Thoughts and the
  `tool_call`/`tool_call_update` records are dropped.
- The text counts only after a successful terminal (`result`). On the desktop this is the same
  moment `StdoutHandler` emits `streamedText`. A run with no terminal, a cancelled `end`, or an
  `error` reads empty. The parser latches the failure, so a later `end` still reads as `error`.
- Output with no native Grok line is returned unchanged. That covers plain text the process
  manager has already extracted, which is what the desktop buffer normally holds, and which may
  itself begin with `{`.
- Every other provider is unchanged.

### `spawnGroupChatAgent.ts`: no change needed

I traced the Grok inputs through the file. The helper is provider-neutral:

moderator path.

## GT1-08-14 IMPLEMENT: Grok utility turns through the context groomer

Date: 2026-11-01. Kind: IMPLEMENT. Local commit only (no push per CONTRACT).

### What was verified before the change

- `groomContext` (`src/main/utils/context-groomer.ts`) is the one main-process utility runner
  for the IPC `context:groomContext` handler (Quick Chat routing, cheap summaries, context
  merge/transfer grooming, consult grooming), AI command mode (`ipc/handlers/aiCommand.ts`),
  Director's Notes synopsis (`ipc/handlers/director-notes.ts` and the web callback) and group
  chat reset (`ipc/handlers/groupChat.ts`). Tab naming does NOT use it: `ipc/handlers/tabNaming.ts`
  owns its own admitted spawn, audited by GT1-08-14E.
- Shared seams it already reuses, retained unchanged: `buildAgentArgs` plus
  `applyAgentConfigOverrides` (model, effort, custom args, selected-account env), the canonical
  prompt-file planner `resolvePromptDelivery` (Grok's `acp-json` artifact, local or remote),
  `wrapSpawnWithSsh` with the loud unresolved-remote failure, `boundUtilityRoute` against the
  managed route ceiling before any side effect, admission through `spawnAdmitted`, and the
  controller-backed cancellation, idle and overall timeouts. The Grok effort retry is already
  suppressed (original failure kept; GT1-02-07C).
- Utility selection is the caller's: `context:groomContext` swaps in `utilityAgentId` and drops
  the session's path/args/env/token source for a different utility agent while keeping SSH.
- Grok definition limits (`src/shared/maestro-lib/providers/definitions.ts`, owned by earlier
  phases, unchanged): `promptFile` route, `readOnlyArgs` `--permission-mode plan --deny Bash(*)`
  with `readOnlyCliEnforced: true`, and deliberately NO `noToolsArgs` (`--tools ""` is ignored by
  the CLI; `--disallowed-tools` accepts unknown names silently and the built-in list is
  version-dependent).
- Defect (B41): `disableTools` was a single flag with two meanings. On Grok's prompt-file route
  it always refused (`Prompt-file grooming cannot enforce disabled tools.`), so every Quick Chat
  routing turn and every AI command suggestion on a Grok agent failed, although both callers
  pair it with `readOnlyMode` and use it to keep a text transform from wandering, not as a
  safety boundary. A caller that truly needed no tools had no way to say so.

### What changed (context-groomer.ts only)

- `disableTools` is now documented and implemented as BEST EFFORT. An agent with `noToolsArgs`
  gets them (unchanged). A legacy route without them is untouched (unchanged). On a prompt-file
  route without them (Grok) the turn falls back to the provider's CLI-enforced read-only
  arguments, logged as `Tools cannot be disabled; grooming falls back to read-only`, and the
  existing check still refuses it when read-only is not CLI-enforced
  (`Prompt-file grooming cannot enforce read-only mode.`).
- New `requireDisabledTools`: the explicit required contract. For an agent with no verified
  `noToolsArgs` it is refused right after detection, before argument building, admission or
  spawn, on every route, with `<display name> cannot run this turn with tools disabled: it has no
verified all-tools-off flag. Nothing was run.` It is never downgraded to the read-only
  fallback, even when `disableTools` and `readOnlyMode` are also set. With a verified flag it
  applies it.
- No `--tools`, `--disallowed-tools` or deny-list is invented; the fallback args are exactly the
  definition's `readOnlyArgs`. Managed refusals are untouched: `boundUtilityRoute` and admission
  run after these checks on the same args, so a refusal there still ends the turn with no
  fallback provider or unmanaged spawn.
- No caller passes `requireDisabledTools` yet (no current consumer needs a hard no-tools
  guarantee); the IPC and preload surface do not carry it. Adding it to a caller is a later,
  caller-owned change.

### Exact unsupported utility guarantees for Grok

| Guarantee                                   | Grok status                                                                                                                                     |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| All tools disabled (`requireDisabledTools`) | Unsupported. Refused before spawn. Needs a qualified all-off flag (Phase 11); never approximated.                                               |
| Best-effort no tools (`disableTools`)       | Delivered as enforced read-only only. Read tools (read_file, grep, list_dir) and MCP tools stay available; shell is denied by `--deny Bash(*)`. |
| Read-only                                   | Supported by CLI policy (`--permission-mode plan --deny Bash(*)`, live on grok 1.0.5); never `--always-approve` on that route.                  |
| System prompt on a utility turn             | Not delivered by this runner for any provider (no caller passes one); any instructions ride inside the prompt-file text.                        |
| Effort retry on refusal                     | Not retried for Grok; the original failure is kept (GT1-02-07C, GT1-08-14E for tab naming and the runtime runner).                              |
| Claude TUI token-source routing             | Claude only by design; Grok always runs its batch prompt-file route.                                                                            |
